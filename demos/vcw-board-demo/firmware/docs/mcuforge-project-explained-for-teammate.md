# 给新队友的 MCUForge 项目说明

## 先用一句话讲明白

**MCUForge 不是造车项目，也不是做一个“会聊天的单片机助手”。它是在做一支能接手 MCU 工程、分工协作、调用真实构建工具、用测试证明结果，并把高风险操作关在人类审批后的 AI 开发团队。**

我们拿一个已经存在的 STM32 工程当案例：它本来有遥控、RS485 电机控制、TFT 等旧功能。比赛 Demo 不碰车辆和电机，而是把控制输入改成电脑虚拟手柄，输出改成 TFT 和 PC 监控中的**虚拟左右输出**。这样就能安全演示：用户提需求后，多个 Agent 怎样把一个尚未完成的功能补齐并验证。

## 1. 为什么要做这个项目

普通 AI 编程助手常见的工作方式是：用户说一句需求，AI 生成一段 C 代码，用户自己猜它能不能编译、接线对不对、烧录后会不会出问题。

单片机开发恰好不能这样赌。它有四个典型难点：

1. **需求容易模糊**：例如“断开控制后要安全停止”，到底多久算断开、怎样恢复、急停是否可解除，都需要明确。
2. **资料分散**：芯片手册、模块用户手册、开源例程、旧工程代码散在不同地方；网上找到的代码也不一定有许可证或适配当前硬件。
3. **工程不是一段代码**：要理解 CubeMX 配置、Keil Target、引脚、外设、已有模块和 PC 工具，不能把内容随手塞进 `main.c`。
4. **“能生成”不等于“能验证”**：真正可信的结果至少应经过构建、固定测试、硬件观测，并保留日志和产物哈希。

MCUForge 的目标就是把这些事情拆成可交接、可检查的流程，而不是让一个 Agent 假装什么都会。

## 2. 我们实际拿什么做 Demo

目前使用的是一个已有的 STM32H723 工程，Keil Target 名为 `VCW`。它原本有 SBUS 遥控输入和 RS485 电机控制代码，但我们没有车辆，也不会让比赛 Agent 直接控制电机。

比赛模式把真实风险隔离开：

```text
电脑虚拟手柄 / 监控软件
          │ USB CDC（COM3）
          ▼
STM32H723 开发板
          ├─ 解析受限的 14 字节控制帧
          ├─ 计算“虚拟左/右输出”
          ├─ TFT 显示输入、输出与安全状态
          └─ 每约 50 ms 回传 JSON 遥测
                    │
                    ▼
              PC 曲线、数值与日志
```

这里的“虚拟左/右输出”只是软件里的模拟值，不会发到真实 RS485 电机链路。这个设计不是退而求其次，而是有意把 Demo 聚焦在**安全的软件开发与验证能力**：我们能看见需求输入、固件状态、TFT 状态和 PC 遥测，同时没有车辆失控风险。

## 3. 这个 Demo 最终要演示什么

最终现场不是展示“车开起来”，而是展示一次完整的开发闭环。推荐的演示需求是：

> “电脑控制帧连续超过 150 ms 没收到时，虚拟左右输出必须清零并进入 `FAILSAFE`；收到急停时进入 `ESTOP` 并锁定；从 `FAILSAFE` 恢复前，需要连续收到 3 帧中位控制。”

随后展示这条链路：

```text
用户提出需求
  ↓
Requirement Agent 把自然语言变成验收合同
  ↓
Research Agent 查工程、手册与可用例程，给出来源和边界
  ↓
Firmware Agent 在允许的文件范围内实现功能并触发 Keil 构建
  ↓
Verification Agent 独立运行固定测试，不允许改测试迎合结果
  ↓
人工批准后才烧录 / 使用 COM3 复测
  ↓
TFT、PC 监控、构建日志和测试报告共同形成证据
```

所以，Demo 的精彩点是：**Agent 的工作过程可以被检查，失败也有去处，成功有真实证据。**

## 5. 五个 Agent 分别干什么

把它理解成一个小型研发组，而不是五个 AI 一起闲聊。

| 角色 | 像团队里的谁 | 具体任务 | 必须交出的东西 | 不能做什么 |
| --- | --- | --- | --- | --- |
| Lead | 项目经理 | 拆任务、安排顺序、判断是否返工 | 任务卡、进度、最终结论 | 不直接偷偷改固件实现 |
| Requirement | 产品/系统工程师 | 把需求讲清楚，明确输入、输出、边界和验收条件 | 验收合同 | 不降低验收标准来“让测试通过” |
| Research | 技术资料工程师 | 查芯片手册、模块说明、可信例程和许可证 | 来源清单、事实卡片、风险结论 | 不复制来源不明的代码 |
| Firmware | 固件工程师 | 在模块边界内实现、调用构建 | 代码改动、构建摘要 | 不改固定测试掩盖问题 |
| Verification | 测试/质量工程师 | 独立构建、跑固定测试、保存证据 | 测试报告、日志、哈希、失败复现 | 不替 Firmware 改实现，不改测试 |

这套分工的核心是**相互制约**：写代码的人不能自己改评分标准，验证的人不能为了赶进度偷偷修实现。

## 6. Skill、MCP、HiClaw 分别是什么

这三个词最容易把人绕晕，其实可以这样理解：

| 名词 | 通俗解释 | 在 MCUForge 里的作用 |
| --- | --- | --- |
| HiClaw / AgentTeams | 安排“谁先做、谁后做、谁交接给谁”的团队系统 | 把五个角色组织起来，不让所有人抢同一件事。 |
| Skill | 一本可复用的工作手册 | 规定如何读工程、如何构建、如何测试、失败后怎么办。 |
| MCP 工具桥 | 一扇带门禁的工具窗口 | 让有权限的 Worker 调用真实 Keil/工程信息，但不能任意操作电脑。 |

例如 `stm32-keil-build` 这个 Skill 会规定：输入是工程路径、Target 和构建模式；输出必须包括错误数、警告数、程序尺寸和 HEX/AXF 哈希；构建失败时不能继续烧录。

受限 MCP 工具桥目前提供的是真实但有限的能力：

- 查看工程快照、跟踪文件和 Git Diff；
- 受限读取文本文件，阻止越界、密钥和大文件；
- 校验固定测试没有被篡改；
- 调用固定包装脚本完成 Keil 构建。

它**没有**任意命令执行、任意文件访问、烧录、串口控制、源码写入或 Git Push。这正是项目可信的原因：Agent 能做有价值的真实工作，但不会因为一句错误指令就接管电脑。

## 7. 为什么不能让 Agent 直接上网抄例程

项目最终会允许 Research Agent 受控检索 GitHub、Gitee、CSDN、厂商网站等资料，但它不能“搜到什么就直接复制”。正确流程是：

1. 优先找芯片/模块的官方数据手册和用户手册；
2. 再找来源、版本、许可证都明确的开源例程；
3. 把关键结论写成带链接和版本信息的事实卡片；
4. 资料冲突、型号不一致或找不到时，明确向用户索要手册或原理图；
5. 把思路转化为适配当前工程的实现，而不是原样搬运。

这样做既防止硬件参数抄错，也避免版权与许可证问题。

## 8. 你作为队友，现在最需要理解和能做的事

你不需要一开始就会写 STM32 驱动。你的价值可以非常具体：

1. **把需求写成验收标准**：例如把“断链后停止”写成“超过 150 ms 无有效帧，`left_cmd=0`、`right_cmd=0`、`state=FAILSAFE`”。
2. **整理资料和来源**：不是贴一堆链接，而是回答“该资料说明了什么、适用哪个型号、是否可信”。
3. **维护证据材料**：截图、构建结果、测试报告、视频片段必须能一一对应到结论。
4. **制作 PPT 和 Demo 讲述**：清楚区分已验证、开发中和计划；不要把车辆、电机或“全自动”夸大进去。
5. **作为独立检查者提问**：看到“测试通过”就问：哪个用例？谁跑的？日志在哪里？有没有改用例？

你暂时不应该做的事也很清楚：没有验收合同时不要催着改代码；没有资料依据时不要让 Agent 猜寄存器；没有人工批准时不要烧录、不要接真实执行器。

## 9. 给你做 PPT 时的 60 秒讲法

可以直接这样说：

> MCUForge 面向的是已经存在、但还没做完的单片机工程。普通 AI 往往只能生成一段代码，而 MCUForge 把需求、资料、固件和验证拆给不同 Agent：先冻结验收标准，再查手册和例程，之后在受限工具桥里理解并构建真实 Keil 工程，最后由独立验证角色跑固定测试、保存证据。我们的 Demo 不控制车辆，而是在 STM32H723 开发板、TFT 和 PC 虚拟手柄上完成同样的开发闭环。这样既能真实验证 Agent 的开发能力，又能把烧录、串口和电机等风险操作留给人工审批。
