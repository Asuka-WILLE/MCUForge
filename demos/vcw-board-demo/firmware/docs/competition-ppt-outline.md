## 1. 核心叙事

MCUForge 不是单纯帮助用户生成单片机代码，而是以 AgentTeams 为协作基点，让多 Agent 接手已有或新建 MCU 工程，完成需求澄清、资料检索、模块化实现、真实构建、烧录审批、硬件复测、证据归档和经验沉淀。

主 Demo 使用一个开发到一半的 STM32H723 工程：工程中已有 BMI088 底层驱动，但初始化、采样、校准、TFT、USB 遥测和 PC 可视化尚未完成。用户提出需求后，由 AgentTeams 完成端到端开发闭环。

## 3. 逐页内容

### 第 1 页：封面

- 标题：`MCUForge：面向单片机开发的可验证多 Agent 协作基础设施`
- 副标题：`从需求澄清、资料检索到真实构建与硬件复测`
- 视觉：开发板/TFT 实拍与 Element 对话局部截图。

### 第 2 页：一页纸速览

- 问题：现有 AI 编程工具通常止步于代码生成，难以自主理解硬件工程、沉淀手册、完成真实构建和硬件复测。
- 方案：基于 AgentTeams 组织需求、研究、固件和验证等职能 Agent，通过可复用 Skill 与受控工具桥形成端到端闭环。
- 差异：真实调用 Keil、串口和开发板；冻结验收标准；验证 Agent 独立复测；器件资料形成可检索知识卡片。
- 复用：项目理解、资料研究、Keil 构建、硬件测试和证据审计可迁移到其他 MCU 项目。
- 进展：Docker Desktop 与 HiClaw 已部署；真实 STM32 工程、Keil 构建、TFT、COM3 遥测、固定测试和证据基线已具备。

### 第 3 页：目录

保持官方模板目录，在页脚补充：`以接手一个开发到一半的 STM32 工程为贯穿案例`。

### 第 4–5 页：场景与价值

章节观点：`AI 会写代码，但还不会完成单片机开发。`

目标用户：嵌入式工程师、高校实验室和竞赛团队、中小型硬件研发团队、缺乏完整测试资源的 MCU 开发者。

四个断点：

1. 意图断点：AI 不主动确认需求和验收标准。
2. 知识断点：手册读完不沉淀，重复消耗上下文。
3. 工程断点：代码容易堆入 `main.c`，缺少模块边界。
4. 验证断点：代码生成后不会真实构建、烧录和复测。

输入：现有工程、器件型号、用户需求、硬件资料。

输出：模块化代码、构建产物、测试证据、知识卡片、审计报告。

复赛评估指标：首次构建通过率、人工反馈次数、任务完成时间、手册重复读取次数、自动验证覆盖率、证据完整率。

### 第 6–7 页：方案总览

章节观点：`从单个代码助手，升级为完整开发团队。`

总体链路：

```text
用户 / Element
      ↓
AgentTeams Manager
      ↓
需求 Agent → 研究 Agent → 固件 Agent → 验证 Agent
      ↓
可复用 Skills
      ↓
互联网 / 本地手册 / Git / Keil / CMSIS-DAP / COM / TFT
      ↓
知识卡片 + 共享状态 + Trace + 证据报告
```

两种模式：

- 已有项目：理解工程 → 发现未完成模块 → 修改 → 真实验证。
- 新项目：确认器件 → 搜索资料与例程 → 生成架构和工程脚手架。

### 第 8–9 页：多 Agent 协同设计

章节观点：`多 Agent 的价值不在角色数量，而在职责隔离和相互验证。`

| Agent | 主要职责 | 禁止事项 |
| --- | --- | --- |
| Manager | 拆解任务、维护状态、组织返工 | 不直接修改实现代码 |
| Requirement | 澄清需求、冻结验收合同 | 不降低验收标准 |
| Research | 检索手册、例程、许可证并生成知识卡片 | 不复制来源不明代码 |
| Firmware | 模块化实现并调用构建 Skill | 不修改固定测试 |
| Verification | 独立构建、申请烧录、硬件复测、证据归档 | 不替实现 Agent 修改代码 |

结构化交接物：验收合同 → 来源清单 → 代码变更与构建结果 → 验证报告。

异常分支：

- 找不到资料：向用户索要。
- 资料冲突：标记冲突并暂停实现。
- 构建失败：退回 Firmware Agent。
- 测试失败：保存原始证据后返工。
- 烧录或推送：必须人工批准。

### 第 10–11 页：Skill 工程体系

核心 Skill：

- `project-intake-map`
- `requirements-contract`
- `component-source-research`
- `stm32-keil-build`
- `stm32-fixed-hardware-test`
- `stm32-evidence-audit`

重点展示 `stm32-keil-build`：输入工程路径、Target 和构建模式；输出错误、警告、程序尺寸和 HEX/AXF 哈希；构建失败时禁止继续烧录；可复用于其他 Keil STM32 项目。

### 第 12–13 页：工具、上下文与安全

章节观点：`Agent 不能直接拿到整台电脑的控制权。`

受控 Windows 工具桥提供：工程读取与搜索、受限补丁、Keil 构建、设备枚举、烧录审批、串口测试和证据归档；不提供任意 Shell。

上下文能力：器件知识卡片、文档版本与哈希、SQLite/FTS 检索、Agent 共享任务状态和历史项目经验。

可观测与安全：Matrix 消息、Skill/MCP Trace、Git diff、产物哈希、烧录审批、失败返工记录和 Git checkpoint/revert。

主 Demo：接手现有 BMI088 半成品驱动，完成初始化、静止零偏、roll/pitch、TFT、USB、PC 监控和硬件验证；不实现无磁力计支撑的绝对 yaw。

### 第 14–15 页：开放与开源

计划开源：Agent Identity 与协作协议、MCU 工程理解和器件研究 Skills、Windows Keil/串口工具桥、知识卡片格式、固定测试与证据模板、BMI088 已有项目示例、F407 电容屏新项目示例。

建议主项目采用 Apache-2.0；厂商手册不重新分发；许可证不明的 CSDN、Gitee、GitHub 或厂商代码只用于事实参考，不直接复制。

### 第 16–17 页：进展与路线图

已完成：Docker Desktop 与 HiClaw、STM32 工程地图、Keil 基线、开发板烧录、TFT、COM3 遥测、固定硬件测试、三个基础 Skill。

复赛目标：五个 Agent 正式运行、Windows Tool Bridge、BMI088 主 Demo、知识卡片、共享状态、Trace、审批与回滚、Demo 视频。

后续扩展：F407 + 野火电容屏新项目模式，以及 CubeMX、CubeProgrammer、PlatformIO 等工具适配。

主要风险：联网资料不稳定、模型输出错误、烧录风险、第三方许可证不清、没有真实车辆。对应使用资料缓存与哈希、固定测试、人工审批、许可证审计，并明确 Demo 只验证开发板/TFT/USB。

### 第 18–19 页：团队

- 自动化专业成员：STM32、Keil、外设、接口边界、烧录审批和硬件验证。
- 数学专业成员：AgentTeams、知识库、结构化数据、PC 工具、评估指标、Trace 与视频材料。

结尾观点：`MCUForge 的目标不是让 AI 多写代码，而是让 AI 对 MCU 开发结果负责。`
