# MCUForge 初赛 PPT：队友逐页制作手册

> **目标**：用官方 19 页模板，讲清 MCUForge 如何让 AgentTeams 接手一个已有 STM32 工程，在受控边界内完成“需求 → 资料 → 实现 → 真实构建 → 固定测试 → 证据”的开发闭环。
>
> **本 PPT 的演示边界**：我们没有车辆，也不把真实 RS485 电机控制当作 Demo。主 Demo 是 **STM32H723 开发板 + TFT + USB CDC（COM3）+ 电脑虚拟手柄/监控工具**。这不是短板：它刻意证明 Agent 能安全地开发和验证嵌入式功能，而不会直接获得电机、烧录、任意 Shell 或整台电脑的权限。

## 0. 做之前先统一三件事

### 0.1 只讲一条主故事

全篇反复回答同一个问题：

> 一个开发到一半的 STM32 项目，用户提出“补上安全断链与测试证据”的需求后，MCUForge 如何让多个 Agent 有分工、有证据地完成开发？

不要把 PPT 写成“我们部署了很多 AI 工具”。评委关心的是：**你的 Agent 为什么比单个聊天机器人更可靠，如何真正落到 MCU 工程。**

### 0.2 统一术语（全篇不要混用）

| 推荐写法 | 含义 | 不要写成 |
| --- | --- | --- |
| `MCUForge` | 我们的项目名 | “一个大模型” |
| `AgentTeams（HiClaw）` | 多 Agent 的组织与编排环境 | “我们自己从零实现的多 Agent 框架” |
| `Skill` | 可复用的工程方法与输入输出规范 | “Prompt” |
| `受限 MCP 工具桥` | 让特定 Worker 调真实工程工具的受控接口 | “Agent 可控制电脑” |
| `虚拟左右输出` | Demo 固件中的安全模拟结果 | “电机已受控” |
| `已验证 / 开发中 / 计划` | 三种事实状态 | 把计划写成已完成 |

### 0.3 事实红线

PPT 内所有“已完成”只能来自证据：

- 已有 STM32H723 / Keil 工程，目标 `VCW` 可真实构建，最近记录为 `0 Error(s), 0 Warning(s)`。
- 比赛 Demo 固件与生产电机控制隔离；USB CDC 接收 PC 14 字节控制帧，约每 50 ms 回传虚拟状态 JSON；PC 工具有虚拟手柄、监控和日志能力。
- HiClaw Team 已有 Leader、Requirement、Research、Firmware、Verification 五种角色；Firmware/Verification 已接入受限 MCP 工具桥，并真实调用过 Keil 构建。
- 当前 Demo 基线已有 `CTRL-001` 成功；`FS-001`、`ESTOP-001`、`REC-001` 是**故意保留给 Agent 完成的任务**，不要标成已通过。
- 不展示电机运动、不声称车辆验证，不泄露令牌、Consumer Key、密码、串口私密日志或本机绝对用户名。

## 4. 图文与排版的硬规则

1. 一页不超过 45 个汉字正文；列表超过 6 条必须改成卡片/流程图。
2. 不使用“赋能、颠覆、全栈、领先”等空词；用具体能力替代，例如“真实 Keil 构建并输出哈希”。
3. 每个架构图只画一个阅读方向：从上到下或从左到右。
4. 所有截图至少占页面面积 30%，保留能证明结论的局部，裁掉无关窗口。
5. 页面标题必须是结论型标题，避免只写“方案设计”。例如：`受限工具桥让 Agent 调用 Keil，而不是控制整台电脑`。
6. 只在深色标题页使用白字；内容页一律深色字 + 白底，保证投影可读。
7. 不把示例图、模板中的 `OpsPilot Zero`、`7×24`、`Nacos/K8s` 等内容留在成品里；这些与项目无关。
8. 图片来源不明时宁可不用；实拍、真实日志、自己画的结构图优先级最高。
